# 提取 micro-benchmark v0.1（待审核）

先阅读 [REVIEW.md](REVIEW.md) 或无需服务即可打开的 [review.html](review.html)。这是预期事实草稿，不是已确认答案。用户审核后再冻结评分规则；当前没有 LLM Judge，也没有把未检查的事实自动算作通过。

## 固定输入

5个测试点，5篇不重复的公开帖子：月行水上单帖、红山两帖合批、红山初始化后增量、音律联觉贩售单帖、绿联官宣单帖。红山的两个测试点复用完全相同的输入，但执行顺序不同。

`inputs/` 仅含公开正文、官方账号来源元数据和配图URL。`suite.json` 固定输入文件SHA-256、分界时间、模拟时间、批大小和预期事实。禁止把这些样本添加到运行时Few-shot后仍作为独立评测样本；本版只衡量纯文本能力。

预期事实不匹配标题字面、数组顺序和稳定ID具体值。日期等机械条件标为 `deterministic_candidate`，表示未来可程序化，但必须先正确定位对应实体；语义项目人工判断。当前所有项目初始状态为 `not_reviewed`，无默认通过。

## 准备一轮实验（不联网）

```powershell
python scripts/micro-benchmark.py --prepare .herald-work/micro-benchmark/round-01
```

每个测试点生成现有回放器可读取的 `dataset.json` 和可填写的 `review.json`，根目录保存测试标准快照、Git版本及关键代码指纹。不覆盖旧目录。生成记录会出现在调试网页的数据集列表中，服务需自行启动；本次构建未重启服务。

审核确认后，可用现有 `scripts/run-local.py --replay bootstrap --replay-directory <测试点目录> --now <suite中now>` 执行真实调用。红山增量点在初始化成功后，再对同目录运行 `--replay incremental`。参数及模型由本地配置或显式环境变量决定；原始实际模型、请求、回答和诊断保存在traces中。初始化批大小沿用正式默认2。

通过调试网页运行会创建新的runs目录；评审时应把该运行目录填入对应实验记录，不能只靠相同文件名认定输入相同。建议一次比较只改一个因素，并重复3次，记录实际请求中的模型、Prompt、Few-shot、批大小、thinking、输出上限、时间、费用可用指标与失败次数。

## 评审顺序

1. 是否真正覆盖计划输入；是否有筛选排除、重试、截断、Schema失败。失败不可从分母中删除。
2. 原始提取：逐条标记 `pass / fail / uncertain / not_applicable`，填写实体和证据。
3. 合并后事实：独立检查，不能用二轮纠错掩盖第一轮错误。
4. 提醒、稳定ID、重复投递是链路检查，单独报告，不混入纯提取准确率。I03重复投递当前需额外回归执行，不能只跑两阶段就勾选通过。

尚未实现自动批量调用及评分汇总。当前交付是可复用的固定输入、逐条预期审阅稿与离线准备工具。评分器应在预期事实经用户审核后实现，避免把存在争议的人工判断固化为代码。

修改期望后更新suite版本，并执行 `python scripts/micro-benchmark.py --render` 重建审阅稿。修改输入需有意更新SHA-256，已运行的旧轮次保留原标准快照。
