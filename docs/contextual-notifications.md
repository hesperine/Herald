# 正式两轮解析与通知

生产入口 `herald.cli._make_provider` 默认启用两轮解析。旧单帖接口留给离线兼容测试及独立提取用途；生产无须新增配置。

## 状态与重试

1. `candidate_stage` 先来源去重和规则筛选，`candidates` 保留可追踪原帖。
2. `contextual_pipeline` 先保存 pending，再按 IP 分批做短语目录归属；每批最多 24 组、60,000 字符，完整请求上限 180,000 字符。超限或接口失败保留 pending，不截断事实。所有新接口受原有调用次数、运行时限和账号冷却约束。
3. `contextual-plans` 保存归属及逐企划完成进度，避免第二个企划失败后重做已完成部分。所有企划完成后才将多对多关系写回候选。
4. 第二轮得到结构化提取和稳定 ID 更新操作。已有实体由 `fact_updates` 校验证据、值类型及时间优先级；重复实体按公开字段比较，不因来源 ID 变化再创建。同一企划另一个不明关系的活动保守新建。
5. 日期必须有对应字段引文。无日期不会漏掉企划公告，但也不会生成未来日期任务。引文校验不等于语义绝对正确，错误仍可通过后续有依据的更新纠正。

## 通知

`campaign_notices` 用实体 ID + 属性名比较公开事实。队列保存将要通知的完整事实快照及覆盖候选 ID，摘要只显示相对已发基线的变化。同一企划的新公告和日期提醒合在一张卡。

`digest-snapshots/YYYY-MM-DD.json` 在发送前保存不含收件人的正文、HTML、任务及回执事实。部分发送失败时沿用该快照。`email-delivery.json` 仍只保存日期和位图，收件人顺序规则不变。当天成功回执继续阻止后续发送，后来新增事项留待次日。

## 升级

`notice-baselines` 在新提取前从旧回执建立基线，补齐旧版未记录的实体名字和状态字段；不会把未发送的旧事实全部标成已读。一次性 `contextual-v2-<ip>` 标记负责把有效旧企划的公开观察记录放回 pending 复核。

明确的旧误归属活动移到 Campaign 的 `excluded_activities`，依据保存在 `scope_reviews`，不是删除、取消或伪造结束。原 ID、原事实、回执仍可追溯；正常 scheduler 重编排清除错误未来提醒。

手动 `Daily collaboration scan` 的 `send_email=false`（默认）可使用远端原配置完成迁移和页面发布，不发邮件。定时 FULL/RETRY 行为不变。

main 的生产代码或 daily 工作流更新会先执行无 Secret 的离线回归，通过后自动运行一次 `retry --no-email` 完成部署刷新。它与定时任务共用并发锁，不进行额外完整采集，不发送邮件。

## 验收

`scripts/production_review.py` 通过 `scripts/run-local.py --production-review <目录>` 注入本地配置，使用 10 月 24、25 日已发布提醒对应的公开原帖运行正式管线，模拟发送只写本地文件，最终扫描产物防止已知私密值进入 state/page。完整请求按哈希缓存便于复核，不记录 Authorization 或私密配置。

离线回归覆盖：多帖单企划、跨日宣传不重发、增量变更、旧回执迁移、一次性复核、部分失败重试、重复实体、误归属归档、日期证据、截断回答、固定邮件快照及同企划消息/日期卡片合并。
